    5. The HTTP functions in Dart

    5.1. Choosing HTTP Tools

    Unlike JavaScript/TypeScript, which provides a [fetch] NATIVE function (both in the browser and in Node.js), Dart does not provide a high-level client PAS in its standard library ([dart:io] exposes only a low-level [HttpClient], which is cumbersome to use directly). Two external packages together cover exactly the same ground as [fetch] and [axios] in the TypeScript package:

    • [package:http] (pub.dev/packages/http), maintained by the Dart team itself: a simple, low-level API, with no global configuration or interceptors—the role of [fetch].
    • [package:dio] (pub.dev/packages/dio): global configuration ([baseUrl], [timeout]), interceptors, enhanced error handling ([DioException.response])—the role of [axios].

    // dart_fetch_01.dart
// Port fetch-01.ts.
// Choice of HTTP tools in Dart: the [http] package (pub.dev/packages/http),
// maintained by the Dart team itself, serves as the native [fetch]
// Node.js/browser—a simple, low-level API with no
// global configuration or interceptors (unlike the [dio] package,
// which itself acts as [axios]—see dart_dio_01.dart).
import 'dart:convert';
import 'package:http/http.dart' as http;

// URL, the base file for the tax calculation server (see the chapter
// "Setting Up a NestJS Server")
const String baseUrl = 'http://localhost:3000/main.php';

// init session
Future<dynamic> initSession() async {
  // [différence avec TypeScript] the [http] package has no options
  // [timeout] on the request itself: the timeout is limited by
  // by wrapping the Future with the [.timeout(...)] extension from dart:async,
  // which works on any IMPORTE QUEL Future (not just the requests
  // HTTP) — a more general mechanism than the AbortSignal.timeout() function from
  // fetch, specific to native fetch.
  final uri = Uri.parse(baseUrl).replace(queryParameters: {
    'action': 'init-session',
    'type': 'json',
  });
  try {
    // asynchronous request—http.get() returns a Future<http.Response>
    final stopwatch = Stopwatch()..start();
    final response = await http.get(uri).timeout(const Duration(seconds: 2));
    // [response] is the entire HTTP response from the server (headers
    // HTTP + body)—it is displayed to show its structure
    print("réponse http en Dart (durée=${stopwatch.elapsedMilliseconds}ms) : "
        "statusCode=${response.statusCode}");
    // You can access the headers HTTP
    print("entêtes de la réponse=${response.headers}");
    // [différence avec TypeScript] unlike fetch, where response.json()
    // is a separate method (a new `Future`), the body of the
    // response http.Response is already fully available as
    // SYNCHRONE (response.body, a String): http.get() has already processed
    // the entire body before returning its result. jsonDecode() is therefore
    // not an asynchronous operation here.
    final objet = jsonDecode(response.body);
    print("réponse json=$objet, type=${objet.runtimeType}");
    return objet;
  } catch (erreur) {
    // We are here because the server responded with an error code, or
    // because the HTTP client threw an exception (network unreachable,
    // timeout...)
    print("erreur fetch en Dart=${erreur.runtimeType}, $erreur");
    // the error is re-triggered
    rethrow;
  }
}

// the `main` function executes the asynchronous function [initSession]
Future<void> main() async {
  try {
    print("requête HTTP vers le serveur en cours "
        "---------------------------------------------");
    final response = await initSession();
    print("succès ---------------------------------------------");
    print("réponse=$response ${response.runtimeType}");
  } catch (erreur) {
    print("erreur ---------------------------------------------");
    print("erreur=$erreur");
  }
}

    Let’s comment on this code:

    • line 30: [http.get(uri).timeout(const Duration(seconds: 2))]: the [http] package does not have a [timeout] option on the request itself - We limit the wait time by wrapping [Future] with the Dart extension [.timeout(...)]:async, which works on N'IMPORTE QUEL [Future], not just HTTP requests.
    • Line 43: [jsonDecode(response.body)]: Unlike [fetch], where [response.json()] is a separate method from ASYNCHRONE, the body of a [http.Response] is already fully available as a SYNCHRONE ([response.body], a [String]): [http.get()] has already waited for the entire body before returning its result.

    // dart_fetch_03.dart
// fetch-03.ts port: maximum timeout and manual cancellation of a request
// HTTP.
import 'package:http/http.dart' as http;

// Basic URL of the tax calculation server (see http/README, the
// PHP server for the original price history; here we target the
// NestJS server—see the chapter “Installing a NestJS server”)
const String baseUrl = 'http://localhost:3000/main.php';

// Example 1: Request with a maximum timeout, using [.timeout(...)]
// (extension of `dart:async` to all `Future` objects—see dart_fetch_01.dart)
Future<void> requeteAvecDelaiMaximum() async {
  print("--- requête avec .timeout() ---");
  try {
    final response = await http
        .get(Uri.parse('$baseUrl?action=init-session&type=json'))
        // If the wait exceeds 2 seconds, [.timeout] resolves the Future as an error
        // with a [TimeoutException]—the Dart equivalent of
        // the fetch function AbortSignal.timeout()
        .timeout(const Duration(seconds: 2));
    print("réponse = ${response.body}");
  } catch (erreur) {
    // if the server does not exist (which is likely in this exercise), or if
    // the timeout is exceeded, [erreur] is either a [TimeoutException] or a
    // [SocketException]/[ClientException], as appropriate
    print("erreur.runtimeType = ${erreur.runtimeType}, message = $erreur");
  }
}

// Example 2: Manual cancellation of a request, for example because
// the user has changed their mind (e.g., they retype in a
// search field).
//
// [ATTENTION, différence de fond avec TypeScript] the [http] packet did not
// cancellation signal PAR REQUÊTE, as in the fetch AbortSignal: the
// only way to cancel is to FERMER LE CLIENT (http.Client.close()) the
// entire request, which cancels TOUTES the pending requests on that client—so
// so you must create a client DÉDIÉ for each request you want to be able to cancel
// on an individual basis, rather than a shared client for the entire application.
Future<void> requeteAnnulableManuellement() async {
  print("--- requête annulée manuellement ---");
  final client = http.Client();

  // We program a "business logic" cancellation after 10 ms (in a real
  // application, this would be, for example, a click on a “cancel” button)
  Future.delayed(const Duration(milliseconds: 10), () {
    print("annulation manuelle déclenchée");
    client.close();
  });

  try {
    final response = await client.get(Uri.parse('$baseUrl?action=init-session&type=json'));
    print("réponse = ${response.body}");
  } catch (erreur) {
    // Closing the client while a request is in progress causes it to fail with
    // a [ClientException]
    print("erreur.runtimeType = ${erreur.runtimeType}, message = $erreur");
  }
}

Future<void> main() async {
  await requeteAvecDelaiMaximum();
  await requeteAnnulableManuellement();
}

    Let’s break down this code:

    • Line 21: [.timeout(const Duration(seconds: 2))] completes the failed [Future] with a [TimeoutException] that exceeded the time limit - the Dart equivalent of [AbortSignal.timeout()] for [fetch].
    • Line 35: [ATTENTION, différence de fond]—the [http] package lacks a cancellation signal (PAS) for PAR and REQUÊTE, just like [AbortController] for [fetch]: the only way to cancel is to cancel FERMER, LE, and CLIENT ([http.Client.close()]) in its entirety, which cancels TOUTES all pending requests on that client—hence the need to create a client DÉDIÉ for the request you want to be able to cancel individually.

    // dart_dio_01.dart
// Ports axios-01.ts and axios-02.ts.
// Choosing HTTP tools in Dart: the [dio] package (pub.dev/packages/dio)
// serves as [axios]—a global configuration (baseUrl, timeout),
// interceptors, enhanced error handling (error.response, such as
// Axios): everything that the [http] package—which is closer to fetch—leaves to the
// calling code (see dart_fetch_01.dart).
import 'package:dio/dio.dart';

// a Dio instance configured once and for all, reused by all
// calls—exactly the role of "axios.defaults" in TypeScript
final Dio dio = Dio(BaseOptions(
  baseUrl: 'http://localhost:3000/',
  connectTimeout: const Duration(seconds: 2),
  receiveTimeout: const Duration(seconds: 2),
));

// init session
Future<dynamic> initSession({required String type}) async {
  try {
    // asynchronous request—dio.get() directly accepts
    // queryParameters, such as axios.request({params: ...})
    final response = await dio.get('main.php', queryParameters: {
      'action': 'init-session',
      'type': type,
    });
    // the server's response is in [response.data] (already decoded into
    // Map/List by Dio if the Content-Type is JSON), exactly like
    // response.data in Axios
    return response.data;
  } on DioException catch (erreur) {
    // the parameter [erreur] is a [DioException]—we display it for
    // to view its structure (equivalent to "console.log(axios error)"
    // discussed in axios-01.ts)
    if (erreur.response != null) {
      // the server reported an error in the status HTTP but it
      // also sent a response: it is in [erreur.response!.data],
      // exactly like [error.response.data] in Axios
      return erreur.response!.data;
    } else {
      // No response at all (network unreachable, timeout, etc.) - the
      // triggers the error again
      rethrow;
    }
  }
}

Future<void> main() async {
  try {
    // 1st attempt, intentionally invalid (type='x' instead of 'json'),
    // to observe how the server—and then DIO—report the error:
    // the server responds anyway (with a business error status), so
    // erreur.response.data is indeed populated, as in axios-01.ts
    print("requête HTTP (type invalide) vers le serveur en cours "
        "---------------------------------------------");
    final reponseInvalide = await initSession(type: 'x');
    print("réponse=$reponseInvalide ${reponseInvalide.runtimeType}");

    // Second attempt, corrected (type='json'), as in axios-02.ts
    print("requête HTTP (type corrigé) vers le serveur en cours "
        "---------------------------------------------");
    final reponse = await initSession(type: 'json');
    print("succès ---------------------------------------------");
    print("réponse=$reponse ${reponse.runtimeType}");
  } catch (erreur) {
    print("erreur ---------------------------------------------");
    print("erreur=$erreur");
  }
}

    Let’s break down this code:

    • Lines 12–15: [Dio(BaseOptions(baseUrl: ..., connectTimeout: ..., receiveTimeout: ...))]: a [Dio] instance configured once and for all, reused by all calls—exactly the role of [axios.defaults] in TypeScript.
    • [response.data]: the server’s response, which was already DÉCODÉE in [Map]/[List] by Dio if [Content-Type] is JSON, exactly like [response.data] in axios.
    • Lines 30–31: [on DioException catch (erreur) { if (erreur.response != null) ... }]: the same distinction as [error.response] in Axios between a AVEC server response error (business error status) and a SANS response error (network unreachable, timeout).

    // dart_dio_02.dart
// axios-03.ts endpoint: chain two requests—HTTP (init-session), then
// authenticate-user (a POST with a body encoded in
// x-www-form-urlencoded).
import 'package:dio/dio.dart';

final Dio dio = Dio(BaseOptions(
  baseUrl: 'http://localhost:3000/',
  connectTimeout: const Duration(seconds: 2),
  receiveTimeout: const Duration(seconds: 2),
));

Future<dynamic> initSession() async {
  try {
    final response = await dio.get('main.php', queryParameters: {
      'action': 'init-session',
      'type': 'json',
    });
    return response.data;
  } on DioException catch (erreur) {
    if (erreur.response != null) {
      return erreur.response!.data;
    }
    rethrow;
  }
}

Future<dynamic> authentifierUtilisateur(String user, String password) async {
  try {
    // POST request with an x-www-form-urlencoded body—Dio automatically encodes
    // automatically encodes a Map as x-www-form-urlencoded if the
    // Content-Type header in the [Options] request, exactly like qs.stringify(...)
    // + the manual header from axios-03.ts
    final response = await dio.post(
      'main.php',
      queryParameters: {'action': 'authentifier-utilisateur'},
      data: {'user': user, 'password': password},
      options: Options(contentType: Headers.formUrlEncodedContentType),
    );
    return response.data;
  } on DioException catch (erreur) {
    if (erreur.response != null) {
      return erreur.response!.data;
    }
    rethrow;
  }
}

// The `main` function executes the asynchronous functions one by one
Future<void> main() async {
  try {
    // init-session
    print("action init-session en cours "
        "---------------------------------------------");
    final reponse1 = await initSession();
    print("succès ---------------------------------------------");
    print("réponse=$reponse1");
    // authenticate-user - [NOTE, as in the original TypeScript
    // origin] this call initiates a new request: HTTP, SANS
    // automatically share the session cookie set by the server with
    // the previous step (neither Dio nor axios do this automatically on the
    // Node/Dart): manually tracking the session cookie is precisely the
    // subject of dart_dio_03.dart, which contains axios-04.ts.
    print("action authentifier-utilisateur en cours "
        "---------------------------------------------");
    final reponse2 = await authentifierUtilisateur('admin', 'admin');
    print("succès ---------------------------------------------");
    print("réponse=$reponse2");
  } catch (erreur) {
    print("erreur ---------------------------------------------");
    print("erreur=$erreur");
  }
}

    • line 38: [Options(contentType: Headers.formUrlEncodedContentType)]: Dio automatically encodes the [Map] passed to [data] into [x-www-form-urlencoded] as soon as this [Content-Type] is specified - the equivalent of [qs.stringify(...)] combined with the manual Axios header.
    • This call starts with a new request, HTTP SANS, which automatically shares the session cookie set by the server in the previous step—neither Dio nor axios does this automatically on the Dart/Node side: manual cookie tracking is the subject of the following script.

    // dart_dio_03.dart
// Carries axios-04.ts: manual tracking of the session cookie between two requests.
import 'package:dio/dio.dart';

final Dio dio = Dio(BaseOptions(
  baseUrl: 'http://localhost:3000/',
  connectTimeout: const Duration(seconds: 2),
  receiveTimeout: const Duration(seconds: 2),
  // We disable the default validation of the HTTP status so that we can
  // inspect an error response ourselves (such as error.response in
  // Axios), without always having to go through a catch block
  validateStatus: (_) => true,
));

// session cookie
const String sessionCookieName = "connect.sid";
String sessionCookie = '';

Future<dynamic> getRemoteData(String path, {
  required String method,
  Map<String, dynamic>? queryParameters,
  Object? data,
  Options? options,
}) async {
  // for the session cookie—we add it ourselves to the headers of
  // each request, exactly like axios-04.ts
  final opts = (options ?? Options(method: method)).copyWith(
    method: method,
    headers: {
      ...?options?.headers,
      'Cookie': sessionCookie,
    },
  );
  // execution of the request HTTP
  final response = await dio.request(
    path,
    queryParameters: queryParameters,
    data: data,
    options: opts,
  );
  // we retrieve the session cookie if it exists—response.headers is an
  // Dio object (not a simple Map like response.headers in
  // Axios); response.headers['set-cookie'] returns a List<String>?
  final setCookie = response.headers['set-cookie'];
  if (setCookie != null) {
    // we look for the session cookie in this list
    for (final entete in setCookie) {
      final resultat = RegExp('^($sessionCookieName.+?);').firstMatch(entete);
      if (resultat != null) {
        // we store the session cookie
        sessionCookie = resultat.group(1)!;
        break;
      }
    }
  }
  // The server's response is in [response.data]
  return response.data;
}

Future<dynamic> initSession() {
  return getRemoteData(
    'main.php',
    method: 'GET',
    queryParameters: {'action': 'init-session', 'type': 'json'},
  );
}

Future<dynamic> authentifierUtilisateur(String user, String password) {
  return getRemoteData(

    • Line 12: [validateStatus: (_) => true]: disables the default validation of status HTTP, so you can inspect an error response yourself without always having to go through a [catch] block—the same choice as axios-04.ts.
    • [response.headers['set-cookie']] returns a [List<String>?]: unlike [response.headers] in Axios (a simple object), Dio’s [response.headers] is a dedicated [Headers] object, whose indexing always returns a list.
    • Line 48: [RegExp('^($sessionCookieName.+?);').firstMatch(entete)]: the session cookie is retrieved and stored manually, then reinserted into the [Cookie] header of each subsequent request—exactly the same pattern as axios-04.ts, adapted for Dio’s API.

    5.2.7. Conclusion

    [package:http] and [package:dio] together cover the entire scope of [fetch] and [axios]: a low-level API close to the protocol, and a feature-rich API with global configuration and enhanced error handling. The specific differences ([timeout] being generic per [Future] rather than per request, lack of individual cancellation, lack of automatic cookie management) will be reflected, in concrete form, in the HTTP clients in the following chapter.
