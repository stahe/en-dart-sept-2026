    7. Database Access

    The TypeScript course devotes three chapters to accessing a MySQL database: the native driver [mysql2], followed by two ORM ([TypeORM] and [Prisma]), using the same example—two databases, [dbpersons] (a single table) and [dbschool] (four related tables: classes, students, subjects, and grades). This chapter is identical to the first one, then combines the two ORM chapters into a single one: Dart has no mature equivalent of [TypeORM] or [Prisma] for MySQL (see the sidebar at the end of the chapter), and rather than forcing an artificial correspondence with either one, we construct a “lightweight ORM” that demonstrates what a ORM actually does, by writing it ourselves.

    7.1. Direct access to the database

    The TypeScript [mysql2] package has no equivalent maintained by the MySQL team itself on the Dart side. An early version of this chapter used [package:mysql1] (pub.dev/packages/mysql1), a widely used pure Dart driver—MySQL—but it turned out to be incompatible with MySQL 8.4 (the version shipped with Laragon): even a query as simple as “select 1” consistently failed with the protocol error “Got packets out of order,” a known and unresolved bug in the package (issues GitHub adamlofts/mysql1_dart #112 and #161). We are therefore now using [package:mysql_client_plus] (pub.dev/packages/mysql_client_plus), an actively maintained fork that has been tested with MySQL 8.x, and whose API — [MySQLConnection.createConnection], [connection.connect], [connection.execute], [connection.close] — remains very similar to that of [mysql2].

    7.1.1. Preparing the [dbpersons] database

    The dbpersons database contains only one table, persons, which uses the same schema as the one used in the Python course (columns id, first\_name, last\_name, age, with a uniqueness constraint on the pair (last\_name, first\_name)). The script sql/create_dbpersons.sql below creates the database, the application user, and the table, then inserts five arbitrary people into it:

    // mysql_01.dart
// Ports databases/mysql/mysql-01.ts.
//
// First step: connect to the MySQL database [dbpersons] then
// disconnect.
//
// [technical choice] the TypeScript package [mysql2] has no direct
// Dart-side equivalent maintained by the MySQL team itself. A first
// version of this chapter used [package:mysql1] (pub.dev/packages/
// mysql1), a widely used pure Dart MySQL driver - but which turned out
// to be incompatible with MySQL 8.4 (shipped with Laragon): even a query
// as trivial as "select 1" systematically failed with the
// protocol error "Got packets out of order" (known, unresolved bug of the
// package). So here we use [package:mysql_client_plus]
// (pub.dev/packages/mysql_client_plus), an actively maintained fork
// tested with MySQL 8.x, whose API - [MySQLConnection.createConnection],
// [connection.connect], [connection.execute], [connection.close] - stays very
// close to that of [mysql2].
import 'package:mysql_client_plus/mysql_client_plus.dart';

// connection to the MySQL database [dbpersons]
// the user's identity is (admpersons, nobody)
const String user = 'admpersons';
const String pwd = 'nobody';
const String host = 'localhost';
const int port = 3306;
const String database = 'dbpersons';

Future<void> main() async {
  // [difference with TypeScript] no union type "MySqlConnection |
  // undefined" here: a nullable field ([MySQLConnection?]) plays the same
  // role - "not connected yet" is represented by [null], exactly
  // as "not connected yet" was represented by [undefined] on the TS side.
  MySQLConnection? connection;
  try {
    print('Connecting to the MySQL DBMS...');
    // [difference with TypeScript] unlike mysql1 (and mysql2),
    // [mysql_client_plus] separates the CREATION of the connection object
    // ([createConnection], which does no network exchange yet) from
    // the actual establishment of the connection ([connect], which negotiates
    // the protocol with the server) - two quite distinct steps, where
    // mysql1 merged them into a single call [MySqlConnection.connect].
    // We only assign [connection] (the nullable variable of the [finally] block)
    // once [connect] has succeeded: if [connect] fails, [connection]
    // stays [null] and the [finally] will not try to close a connection
    // that was never really opened.
    final newConnection = await MySQLConnection.createConnection(
      host: host,
      port: port,
      userName: user,
      password: pwd,
      databaseName: database,
    );
    await newConnection.connect();
    connection = newConnection;
    // follow-up
    print(
      "Successful MySQL connection to database=$database, host=$host as user=$user, passwd=$pwd",
    );
  } catch (error) {
    // display the error
    print("The following error occurred: $error");
  } finally {
    // close the connection if it was opened
    if (connection != null) {
      await connection.close();
    }
  }
}

    Let’s comment on this code:

    • line 19: [import 'package:mysql_client_plus/mysql_client_plus.dart';]: the new MySQL driver written entirely in Dart, replacing [package:mysql1]—which is incompatible with MySQL 8.4 (included with Laragon): even a query as trivial as “select 1” would consistently fail with the protocol error “Got packets out of order,” a known and unresolved bug in the package (see the comment at the top of the file).
    • Line 34: [MySQLConnection? connection;]: a NULLABLE field serves exactly the same purpose as the union type [MySqlConnection | undefined] of TypeScript - [null] represents “not yet connected,” just like [undefined] relative to TS.
    • Lines 47–55: [final newConnection = await MySQLConnection.createConnection(...); await newConnection.connect(); connection = newConnection;]: [mysql_client_plus] separates the CREATION of the connection object ([createConnection], which is not yet exchanging any network traffic) to the actual establishment of the connection ([connect], which negotiates the protocol with the server)—two distinct stages, whereas [mysql1] (like [mysql2] on the TypeScript side) combined them into a single call. [connection] (the nullable variable from [finally]) is assigned only after [connect] succeeds, so that [finally] never closes a connection that was never actually opened.
    • [try] / [catch] / [finally]: structure identical to the previous version—the connection is always closed in [finally], regardless of whether an error occurred.

// Ports databases/mysql/mysql-02.ts.
//
// In this new script, the database connection is isolated in a
// function.
import 'package:mysql_client_plus/mysql_client_plus.dart';

// connects then disconnects (login, pwd) from database [database] on server
// [host]; throws an exception if there is a problem
Future<void> connect(String host, int port, String database, String login, String pwd) async {
  MySQLConnection? cnx;
  try {
    // connection - [createConnection] creates the object, [connect] really
    // negotiates with the server (see the comment in mysql_01.dart); we
    // only assign [cnx] after a successful [connect], so that the [finally]
    // never closes a connection that did not succeed
    final newConnection = await MySQLConnection.createConnection(
      host: host,
      port: port,
      userName: login,
      password: pwd,
      databaseName: database,
    );
    await newConnection.connect();
    cnx = newConnection;
    print(
      "Successful connection to database=$database, host=$host as user=$login, passwd=$pwd",
    );
  } finally {
    // close the connection if it was opened
    if (cnx != null) {
      await cnx.close();
      print('Successful disconnection\n');
    }
  }
}

// ---------------------------------------------- main
// connection credentials
const String user = 'admpersons';
const String passwd = 'nobody';
const String host = 'localhost';
const int port = 3306;
const String database = 'dbpersons';

Future<void> main() async {
  // connection of an existing user
  try {
    await connect(host, port, database, user, passwd);
  } catch (error) {
    // display the error
    print('$error');
  }

  // connection of a non-existent user
  try {
    await connect(host, port, database, 'xx', 'xx');
  } catch (error) {
    // display the error
    print('$error');
  }
}

    • Lines 10–36: [Future<void> connect(String host, int port, String database, String login, String pwd) async { ... }]: The connection is encapsulated in a reusable function, which throws an exception in case of failure rather than catching it itself—it’s up to the caller to decide what to do with it. It reuses the “creation + [connect()]” pattern from [mysql_01.dart]: [cnx] is only assigned after a successful [connect].

    • [main] calls this function twice, in two separate blocks, [try] and [catch]: once with valid identifiers and once with invalid identifiers, to illustrate both paths.

// connection: we (re)create the [persons] table of the [dbpersons] database.

import 'package:mysql_client_plus/mysql_client_plus.dart';

// executes an update query on the connection
Future<void> executeSql(MySQLConnection connection, String query) async {
  await connection.execute(query);

// ---------------------------------------------- main
// connection credentials
const String id = 'admpersons';
const String pwd = 'nobody';
const String host = 'localhost';
const int port = 3306;
const String database = 'dbpersons';

Future<void> main() async {
  // we go step by step
  late final MySQLConnection connection;
  try {
    // connection - [package:mysql_client_plus], like mysql1 before it,
    // executes by default each query in its own auto-committed
    // transaction (equivalent of AUTOCOMMIT=True on the Python side)
    connection = await MySQLConnection.createConnection(
      host: host,
      port: port,
      userName: id,
      password: pwd,
      databaseName: database,
    );
    await connection.connect();
  } catch (error) {
    print("The following error occurred: $error");
    // [difference with TypeScript] `process.exit(1)` becomes `exit(1)`
    // (dart:io) - same semantics, same process exit code
    exit(1);
  }

  // deletion of the persons table if it exists
  // if it does not exist an error will occur - we ignore it
  try {
    await executeSql(connection, 'drop table persons');
  } catch (_) {
    // ignored - the [_] says we do not care about the exception's value
  }

  // creation of the persons table
  const query = 'create table persons (id int PRIMARY KEY, first_name varchar(30) NOT NULL, last_name varchar(30) NOT NULL, '
      'age integer NOT NULL, unique(last_name,first_name))';
  try {
    await executeSql(connection, query);
    print('$query: query succeeded');
  } catch (error) {
    print("The following error occurred: $error");
  } finally {
    await connection.close();
  }
}

    Let’s comment on this code:

    • Lines 10–12: [Future<void> executeSql(MySQLConnection connection, String query) async { await connection.execute(query); }]: a utility function to execute a SQL update command (here, a DROP TABLE followed by a CREATE TABLE) - [connection.execute(...)] replaces [connection.query(...)] from [mysql1] (same role, new method name on the [mysql_client_plus] side).
    • Line 41: [exit(1);] (from [dart:io]): equivalent to [process.exit(1)]—same semantics, same process exit code in the event of a connection failure.
    • Line 47: [try { await executeSql(connection, 'drop table persons'); } catch (_) {}]: The fact that [_] is passed as a parameter to [catch] indicates that the exception value is being ignored—the table may simply not exist yet.

    // mysql_module.dart
// Ports databases/mysql/mysql-module.ts: reusable functions to
// execute a list (or a file) of SQL commands on an open MySQL
// connection.
//
// [migration] this file initially used [package:mysql1], which turned out
// to be incompatible with MySQL 8.4 (see the comment in pubspec.yaml). It has
// been ported to [package:mysql_client_plus] - see below the difference
// this makes for transaction handling.
import 'dart:io';
import 'package:mysql_client_plus/mysql_client_plus.dart';

// displays the result of an SQL command (result of an execute() of
// mysql_client_plus)
// - if [results.cols] is not empty, it was a SELECT: we display the
//   columns then the rows;
// - otherwise, it was an update statement (INSERT/UPDATE/DELETE/DDL): we
//   display the number of modified rows ([results.affectedRows],
//   equivalent of a cursor's [rowcount]).
void _displayInfo(IResultSet results) {
  if (results.cols.isNotEmpty) {
    // it was a SELECT - [cols] describes the requested columns
    final titles = results.cols.map((c) => c.name).toList();
    final header = titles.join(', ');
    print(header);
    print('*' * header.length);
    for (final row in results.rows) {
      print(titles.map((t) => row.colByName(t)).toList());
    }
    print('*' * header.length);
  } else {
    // no columns described - update statement
    print('number of modified rows: ${results.affectedRows}');
  }
}

// uses the open connection [connection]
// executes on this connection the SQL commands contained in the list
// [sqlCommands] (one command per element; empty lines or lines
// starting with # are ignored)
// - if verbose=true, each execution of an SQL statement is followed by a
//   display indicating its success or failure;
// - if stop=true, the function stops at the 1st error encountered,
//   otherwise it executes all the commands;
// - if withTransaction=true, any error cancels all the SQL statements
//   executed before (rollback); otherwise each command is committed
//   independently (default behaviour of MySQL, in AUTOCOMMIT);
// the function returns a list [error1, error2, ...]
//
// [difference with TypeScript] mysql2 directly exposes
// `connection.beginTransaction()/commit()/rollback()`. [package:mysql1]
// (used in a first version of this file) did not expose these
// methods one by one: the transaction had to be driven "by hand", by
// sending the SQL statements [START TRANSACTION], [COMMIT] and
// [ROLLBACK] ourselves. [package:mysql_client_plus] finally brings the direct equivalent
// of mysql2: `connection.transactional<T>((cnx) async { ... })` executes the
// callback in a transaction, commits (COMMIT) automatically if it
// ends normally, and cancels (ROLLBACK) automatically if it throws an
// exception - no more transaction-control SQL statements to write
// ourselves.
Future<List<String>> executeListOfCommands(
  MySQLConnection connection,
  List<String> sqlCommands, {
  bool verbose = false,
  bool stop = true,
  bool withTransaction = true,
}) async {
  final errors = <String>[];

  // actually executes the commands on the supplied connection [cnx]: it is
  // either [connection] itself (no transaction), or the "working"
  // connection that [transactional] gives its callback (with
  // transaction) - the loop is written only once for both cases
  Future<void> executeCommands(MySQLConnection cnx) async {
    for (final rawCommand in sqlCommands) {
      // remove the leading and trailing blanks of the current command
      final command = rawCommand.trim();
      // empty command or comment? move on to the next one
      if (command == '' || command[0] == '#') {
        continue;
      }
      // execution of the current command
      try {
        final results = await cnx.execute(command);
        // no error
        if (verbose) {
          print('[$command]: Successful execution');
        }
        _displayInfo(results);
      } catch (error) {
        final msg = '$command: Error ($error)';
        errors.add(msg);
        if (verbose) {
          print(msg);
        }
        // do we stop?
        if (withTransaction || stop) {
          // with transaction: we rethrow the error so that
          // [connection.transactional] triggers the ROLLBACK - with
          // [package:mysql_client_plus], it is the EXCEPTION that drives
          // the cancellation, not a mere loop exit as with the
          // manual ROLLBACK of the mysql1 version
          if (withTransaction) rethrow;
          return;
        }
      }
    }
  }

  if (withTransaction) {
    try {
      await connection.transactional((cnx) => executeCommands(cnx));
    } catch (_) {
      // the error has already been recorded in [errors] above; we
      // swallow it here to return the list of errors normally to
      // the caller, exactly as the mysql1 version did (which never
      // let an exception escape from this function)
    }
  } else {
    await executeCommands(connection);
  }
  return errors;
}

// uses the open connection [connection]

// Parameterized queries: single prepared insertion, then bulk
// insertion. Here we recreate the [persons] table with the [id]-column schema
// (as in script mysql_03), so that this script is independent of

import 'package:mysql_client_plus/mysql_client_plus.dart';

// the user's identity

const String pwd = 'nobody';
// the DBMS host machine

const int port = 3306;
// identity of the database

// [difference with TypeScript] `type Person = [id: number, lastName: string,
// firstName: string, age: number]` (a TypeScript tuple, named but still
// a plain array at runtime) becomes here a Dart 3 POSITIONAL RECORD
// (see dart-fundamentals/dart3/dart3_01_records.dart): same idea of a
// "small group of typed values, with no class to write", but a real
// type in its own right, distinct from a [List].
typedef Person = (int id, String lastName, String firstName, int age);

Future<void> main() async {
  // list of persons (id, lastName, firstName, age)
  final persons = <Person>[
    for (var i = 0; i < 5; i++) (i, 'l0$i', 'f0$i', i + 10),
    (40, "d'Aboot", "Y'éna", 18),
  ];

  // another list of persons
  final otherPersons = <Person>[
    for (var i = 0; i < 5; i++) (i + 100, 'l1$i', 'f1$i', i + 20),
    (200, "d'Aboot", "F'ilhem", 34),
  ];

  // access to the DBMS
  MySQLConnection? connection;
  try {
    // connection - we only assign [connection] once [connect] has succeeded
    // (see the comment in mysql_01.dart)
    final newConnection = await MySQLConnection.createConnection(
      host: host,
      port: port,
      userName: id,
      password: pwd,
      databaseName: database,
    );
    await newConnection.connect();
    connection = newConnection;

    // (re)creation of the table with the [id]-column schema (see mysql_03)
    await connection.execute('drop table if exists persons');
    await connection.execute(
      'create table persons (id int PRIMARY KEY, first_name varchar(30) NOT NULL, last_name varchar(30) NOT NULL, '
      'age integer NOT NULL, unique(last_name,first_name))',
    );

    // deletion of the existing records
    await connection.execute('delete from persons');
    // person-by-person insertions with a parameterized query -
    // destructuring of the positional record [person] directly in
    // the for header (see dart-fundamentals/dart3/dart3_02_patterns.dart)
    //
    // [difference with TypeScript and with mysql1] mysql2 (and mysql1, in
    // a first version of this script) use POSITIONAL
    // PLACEHOLDERS ("?", associated with a LIST of values in the same
    // order). [package:mysql_client_plus] works differently: the
    // placeholders are NAMED (":id", ":last_name"...) and associated with a [Map]
    // (placeholder name -> value) - more verbose to write here, but it
    // makes each query independent of the ORDER of the parameters.
    for (final (idP, lastName, firstName, age) in persons) {
      await connection.execute(
        'insert into persons(id,last_name,first_name,age) values(:id,:last_name,:first_name,:age)',
        {'id': idP, 'last_name': lastName, 'first_name': firstName, 'age': age},
      );
    }
    // [difference with TypeScript] mysql2 offers
    // `connection.query('insert ... values ?', [[[...],[...],...]])`, which
    // builds by itself a single multi-row query from an
    // array of arrays. [package:mysql_client_plus] has no such
    // equivalent (like mysql1 before it): so we build the SQL text
    // ourselves, with a group of NAMED placeholders per row (":id0",
    // ":last_name0"... ":id1", ":last_name1"...) since named placeholders
    // cannot be repeated in the same query - a single network
    // round trip, like the TypeScript version.
    final placeholderGroups = <String>[];
    final values = <String, Object?>{};
    for (var i = 0; i < otherPersons.length; i++) {
      final (idP, lastName, firstName, age) = otherPersons[i];
      placeholderGroups.add('(:id$i,:last_name$i,:first_name$i,:age$i)');
      values['id$i'] = idP;
      values['last_name$i'] = lastName;
      values['first_name$i'] = firstName;
      values['age$i'] = age;
    }
    await connection.execute(
      'insert into persons(id,last_name,first_name,age) values ${placeholderGroups.join(',')}',
      values,
    );

    // committing the transaction - here each query has already been
    // auto-committed (MySQL is in AUTOCOMMIT mode by default, like the default
    // mode mentioned in script mysql_03); so there is nothing to commit
    // explicitly
    print('${persons.length + otherPersons.length} persons inserted.');
  } catch (error) {
    print("The following error occurred: $error");
  } finally {
    if (connection != null) {
      await connection.close();
    }
  }
}

    7.1.9. Conclusion

    The port of the native driver is faithful to the original TypeScript. After an initial attempt with [package:mysql1]—which was abandoned due to incompatibility with MySQL 8.4— [package:mysql_client_plus] ultimately provides a API that is even closer to [mysql2] than [mysql1] was: [connection.transactional(...)] is the direct equivalent of [beginTransaction()]/[commit()]/[rollback()], whereas [mysql1] would have required manually managing the transaction using the commands SQL, [START TRANSACTION], [COMMIT], and [ROLLBACK]. One difference remains, albeit a more subtle one: the columns DECIMAL ([subjects.coefficient], [grades.value] in the [dbschool] database) require an explicit conversion using a small helper [_decimal] ([typedColByName<String>(...)] then [num.parse(...)]), since direct conversion to [num] or [double] is not supported by the driver for this SQL type.

    7.2. The lightweight ORM

    The TypeScript course devotes two separate chapters to accessing databases via a ORM ([Object-Relational Mapping]): [TypeORM], followed by [Prisma], using the same example schema. Both are based on a common principle: describe the schema once (using TypeORM decorators on classes, or a [.prisma] file for Prisma), then letting the tool generate, at startup or during compilation, all the code that translates object reads/writes into SQL—including the loading of relationships between tables.

    Dart does not have a mature and widely adopted equivalent to these two tools for MySQL: there are Dart ORM libraries, but they are primarily designed for Flutter/SQLite ([Drift], [Floor]) or for different architectures - Prisma itself does not offer a Dart client. Rather than forcing an artificial mapping such as “such-and-such Dart package = TypeORM” or “such-and-such package = Prisma,” this chapter takes a different approach, one that is more educationally sound: showing what a ORM actually does by writing it yourself in a deliberately minimal version—hence the name [light ORM].

    // repository.dart
// A hand-written "light ORM": a generic [Repository] class strongly
// inspired by TypeORM's Repository (`AppDataSource.getRepository(...)`,
// `.find()`, `.findOneBy()`, `.save()`, `.delete()`), but built on
// a single table, with no decorators nor automatic loading of
// relationships - see README.md for the full discussion of this choice.
//
// [migration] this file initially used [package:mysql1]; it has been
// ported to [package:mysql_client_plus] (see the comment in
// pubspec.yaml). The most visible change for the caller is the
// style of the parameterized queries: mysql1 used POSITIONAL
// placeholders ("?" + list of values in order), whereas
// [mysql_client_plus] uses NAMED placeholders (":column" + a
// [Map] column name -> value) - which, here, fits rather well
// since this repository already handles [Map<String, Object?>] of
// columns.
import 'package:mysql_client_plus/mysql_client_plus.dart';

// [T]: the type of the entity managed by this repository (Person, SchoolClass...)
class Repository<T> {
  final MySQLConnection connection;
  // name of the SQL table
  final String table;
  // name of the primary key column
  final String keyColumn;
  // builds a [T] entity from an SQL result row
  final T Function(ResultSetRow row) fromRow;
  // returns the SQL columns (column name -> value) of a [T] entity,
  // primary key INCLUDED (useful for insertion as well as for
  // update)
  final Map<String, Object?> Function(T entity) toColumns;
  // extracts the primary key value of a [T] entity
  final Object? Function(T entity) key;

  Repository(
    this.connection, {
    required this.table,
    required this.keyColumn,
    required this.fromRow,
    required this.toColumns,
    required this.key,
  });

  // equivalent of `repo.find({ order: { column: 'ASC' } })`
  Future<List<T>> findAll({String? orderBy}) async {
    final sql = 'select * from $table${orderBy != null ? ' order by $orderBy' : ''}';
    final results = await connection.execute(sql);
    return results.rows.map(fromRow).toList();
  }

  // equivalent of `repo.findOneBy({ column: value })` - [conditions] is
  // an "AND" equality on each supplied column; the keys of [conditions]
  // serve both as SQL column name and as NAMED placeholder
  // name (":column") - so they are reused as is as
  // query parameters
  Future<T?> findOneBy(Map<String, Object?> conditions) async {
    final where = conditions.keys.map((c) => '$c = :$c').join(' and ');
    final results = await connection.execute(
      'select * from $table where $where limit 1',
      conditions,
    );
    if (results.rows.isEmpty) return null;
    return fromRow(results.rows.first);
  }

  // equivalent of `repo.findOneByOrFail(...)` / `findOneOrFail(...)`
  Future<T> findOneByOrFail(Map<String, Object?> conditions) async {
    final found = await findOneBy(conditions);
    if (found == null) {
      throw StateError('No row found in [$table] for $conditions');
    }
    return found;
  }

  // equivalent of `repo.save(entity)`: insertion if the key does not exist
  // yet, update otherwise - exactly the "upsert" behaviour of
  // `save()` on the TypeORM side
  Future<void> save(T entity) async {
    final columns = toColumns(entity);
    final currentKey = key(entity);
    final alreadyExists = await findOneBy({keyColumn: currentKey}) != null;
    if (alreadyExists) {
      final toUpdate = columns.keys.where((c) => c != keyColumn);
      final assignments = toUpdate.map((c) => '$c = :$c').join(', ');
      // the columns to update, PLUS the key (under the same placeholder
      // name as in the WHERE clause) - no collision possible
      // since [keyColumn] has precisely been excluded from [toUpdate]
      final values = <String, Object?>{
        for (final c in toUpdate) c: columns[c],
        keyColumn: currentKey,
      };
      await connection.execute('update $table set $assignments where $keyColumn = :$keyColumn', values);
    } else {
      final names = columns.keys.join(',');
      final placeholders = columns.keys.map((c) => ':$c').join(',');
      await connection.execute('insert into $table ($names) values ($placeholders)', columns);
    }
  }

  // equivalent of `repo.delete({ column: value })`
  Future<void> delete(Map<String, Object?> conditions) async {
    final where = conditions.keys.map((c) => '$c = :$c').join(' and ');
    await connection.execute('delete from $table where $where', conditions);
  }
}

// Ports databases/typeorm/typeorm-03-joined-queries.ts.
//
// Highlights the SQL queries that must be written to fetch
// information spread over several tables - what TypeORM
// triggers for you behind the `relations` option, via an SQL JOIN
// (`JOIN`). Unlike orm_02_school.dart (which simulated loading a
// relationship with TWO separate queries, to keep it simple), this file
// writes the REAL SQL joins - exactly what TypeORM does behind
// the scenes, but made entirely visible.
//
// [fundamental difference with TypeScript] TypeORM (like SQLAlchemy, used
// by the original Python course) does NOT do lazy loading by default
// on "classic" entities: the relationships to load must be requested
// explicitly, with the `relations` option. Our "light ORM"
// pushes this principle even further, since here there is NEITHER lazy
// loading NOR "magic" relationship loading: each join is
// SQL written by hand, line by line - the price to pay for depending
// on no object-relational mapping library.
//
// [mysql_client_plus migration] as in repository.dart, the
// positional placeholders ("?") of mysql1 become NAMED
// placeholders (":id", ":name"...), and access to the columns of a
// result row ([row.fields['x']] with mysql1) becomes a typed call
// ([row.typedColByName<T>('x')]).

import 'entities.dart';

// [subjects.coefficient]) as a [num]. [package:mysql_client_plus] can
// convert a DECIMAL to [String] (any SQL type can be read
// as [String]), but NOT directly to [num] or [double] -
// `typedColByName<num>(...)` then throws "Cannot convert MySQL type 246 to
// requested type num" (246 = NEWDECIMAL, the internal MySQL type of

// student by id, with their class (JOIN students/classes)
Future<Student> _studentWithClass(MySQLConnection cnx, int id) async {

    'select s.id as s_id, s.last_name as s_last_name, s.first_name as s_first_name, s.class_id as s_class_id, '
    'c.id as c_id, c.name as c_name '
    'from students s join classes c on s.class_id = c.id where s.id = :id',
    {'id': id},
  );
  final row = results.rows.first;
  return Student(
    id: row.typedColByName<int>('s_id')!,
    lastName: row.typedColByName<String>('s_last_name')!,
    firstName: row.typedColByName<String>('s_first_name')!,
    classId: row.typedColByName<int>('s_class_id')!,

  );

// class by id, with the list of its students (JOIN classes/students)
Future<SchoolClass> _classWithStudents(MySQLConnection cnx, int id) async {

    'select c.id as c_id, c.name as c_name, s.id as s_id, s.last_name as s_last_name, s.first_name as s_first_name '
    'from classes c left join students s on s.class_id = c.id where c.id = :id',
    {'id': id},

  final schoolClass = SchoolClass(id: firstRow.typedColByName<int>('c_id')!, name: firstRow.typedColByName<String>('c_name')!);
  schoolClass.students = [
    for (final row in results.rows)
      Student(
        id: row.typedColByName<int>('s_id')!,
        lastName: row.typedColByName<String>('s_last_name')!,
        firstName: row.typedColByName<String>('s_first_name')!,
        classId: schoolClass.id,
      ),
  ];
  return schoolClass;

    {'name': name},
  );

// grades of a student, with the subject of each grade (double JOIN)
Future<Student> _studentWithGradesAndSubject(MySQLConnection cnx, int id) async {
  final studentRow = (await cnx.execute('select id, last_name, first_name, class_id from students where id = :id', {'id': id})).rows.first;
  final student = Student(
    id: studentRow.typedColByName<int>('id')!,
    lastName: studentRow.typedColByName<String>('last_name')!,
    firstName: studentRow.typedColByName<String>('first_name')!,
    classId: studentRow.typedColByName<int>('class_id')!,
  );
  final results = await cnx.execute(
    'select g.id as g_id, g.value as g_value, sub.id as sub_id, sub.name as sub_name, sub.coefficient as sub_coefficient '
    'from grades g join subjects sub on g.subject_id = sub.id where g.student_id = :id',
    {'id': id},
  );
  student.grades = [
    for (final row in results.rows)
      Grade(
        id: row.typedColByName<int>('g_id')!,
        value: _decimal(row, 'g_value'),
        studentId: student.id,
        subjectId: row.typedColByName<int>('sub_id')!,
        subject: Subject(
          id: row.typedColByName<int>('sub_id')!,
          name: row.typedColByName<String>('sub_name')!,
          coefficient: _decimal(row, 'sub_coefficient'),
        ),
      ),
  ];

}

// Ports databases/typeorm/typeorm-04-stats.ts.
//
// Computes, for a given student, their average weighted by the coefficients
// of the subjects, as well as their min and max grade.
//
// [difference with TypeScript] typeorm-04-stats.ts warned that the
// MySQL `decimal` columns (here grade.value and subject.coefficient)
// are returned by the mysql2 driver as CHARACTER
// STRINGS at runtime (so as not to lose precision), despite their
// declared type `number` - a classic TypeScript pitfall, where the
// static type can lie about the real value at runtime. On the Dart side,
// [package:mysql_client_plus] has a similar pitfall, but made VISIBLE by the
// compiler rather than hidden at runtime: typed access
// (`typedColByName<T>(...)`) can convert a DECIMAL column
// (internal SQL type 246, "NEWDECIMAL") neither to [num] nor to [double] - it
// throws `MySQLProtocolException: Cannot convert MySQL type 246 to requested
// type num`. The only conversion guaranteed for ANY SQL type is
// [String]; so we read the DECIMAL columns as [String] with
// `typedColByName<String>(...)`, then convert them ourselves with
// [num.parse] - see [_decimal] below.
import 'package:mysql_client_plus/mysql_client_plus.dart';

// reads an SQL DECIMAL/NUMERIC column as a [num] (see the comment at the
// top of the file)
num _decimal(ResultSetRow row, String column) => num.parse(row.typedColByName<String>(column)!);

// computes the statistics (weighted average, min, max) of a student
Future<void> _studentStats(MySQLConnection cnx, int studentId) async {
  final studentRow = (await cnx.execute('select id, last_name, first_name from students where id = :id', {'id': studentId})).rows.first;
  print(
    'Statistics of student {"id":${studentRow.typedColByName<int>('id')},"lastName":"${studentRow.typedColByName<String>('last_name')}","firstName":"${studentRow.typedColByName<String>('first_name')}"}',
  );

  final grades = await cnx.execute(
    'select g.value as value, sub.name as subject_name, sub.coefficient as coefficient '
    'from grades g join subjects sub on g.subject_id = sub.id where g.student_id = :id',
    {'id': studentId},
  );

  if (grades.rows.isEmpty) {
    print('  no grades.');
    return;
  }

  num weightedSum = 0;
  num coefficientsSum = 0;
  num min = double.infinity;
  num max = double.negativeInfinity;

  for (final row in grades.rows) {
    // explicit conversion via [_decimal] (see the note at the top of the file):
    // [value] and [coefficient] are thus real [num]s, not strings
    final value = _decimal(row, 'value');
    final coefficient = _decimal(row, 'coefficient');
    weightedSum += value * coefficient;
    coefficientsSum += coefficient;
    if (value < min) min = value;
    if (value > max) max = value;
    print(
      '  grade=${value.toStringAsFixed(2)} subject="${row.typedColByName<String>('subject_name')}" '
      '(coefficient ${coefficient.toStringAsFixed(2)})',
    );
  }

  final average = weightedSum / coefficientsSum;
  print('  weighted average=${average.toStringAsFixed(2)}, min=${min.toStringAsFixed(2)}, max=${max.toStringAsFixed(2)}');
}

    7.2.7. What the lightweight ORM does not do

    Unlike TypeORM/Prisma: no schema generation ([synchronize]/migrations), no decorators, no lazy loading or identity cache, no query builder ([QueryBuilder]), and loading a relationship is ALWAYS a second query or a hand-written join—never automatic. This is a deliberate compromise: enough to illustrate the repository pattern using the example from the course, without claiming to replace a real repository in production.
